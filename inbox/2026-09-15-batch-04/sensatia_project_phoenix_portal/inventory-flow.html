Scenario explorer

Di mana stock berubah?

Retail sale

Working model: retail transaction decreases shopstock for the relevant _shop_id + _item_id. It should not directly deduct DC/warehouse stock.

Evidence to capture

Actual code path, history record, sale document link, legacy exceptions and reconciliation method.

Warehouse → DC

Reduce source warehouse stock, increase destination DC stock. Target model uses warehouse/DC movement, not “warehouse-as-shop” legacy patterns.

To verify

Exact transfer transaction, idempotency behavior, ledger entries and rollback/reversal path.

Warehouse/DC → Retail Shop

Restock/refill increases shopstock and decreases the correct source location. CSV delta / external inventory updates are separate integration effects.

To verify

Which legacy refill paths still use warehouse-as-shop semantics and which paths already use explicit warehouse/DC locations.

E-commerce pack / ship

Working model: order has _fulfillment_warehouse_id; pack is primary DC deduction, with ship fallback for legacy behavior.

Risk

Duplicate deduction or fallback ambiguity if pack/ship behavior is not fully understood and tested.

Stock opname

Positive or negative adjustment should create an auditable movement at the relevant shop or warehouse/DC location.

Evidence

Adjustment authorization, before/after quantity, reason, history/ledger and reconciliation output.

Warehouse/DC keys

_warehouse_id + _item_id
Target source of truth is per-warehouse stock. item.quantity is treated as legacy/denormalized in the current working context.

Retail keys

_shop_id + _item_id
Retail stock is separate from ecommerce fulfilment/DC. This separation is important for OOS, transfer, replenishment and reconciliation.
