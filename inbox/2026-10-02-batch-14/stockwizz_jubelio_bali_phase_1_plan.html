04 · Current state

Mengapa buffer ada sekarang

Sekarang

Retail → Shops → Bali Ecommerce → Sales

Transaksi Jubelio dimasukkan manual, disimpan sebagai shopsales, lalu mengurangi shopstock. Field Jubelio Order ID sudah ada tetapi masih opsional.

→

Target Phase 1

Distribution Center → Bali Ecommerce → Sales

Webhook membuat websales, status disinkronkan, fulfillment terjadi di Bali, dan physical movement memakai warehousestock.

Bali Ecommerce juga menangani Web Sales dari stok fisik yang sama. Namun kode saat ini mencatat Web Sales pada webstock, sementara manual Jubelio memakai shopstock. Dua saldo ini tidak memiliki reservasi bersama sehingga buffer dipakai agar unit fisik yang sama tidak terjual dua kali.

Stok fisik Bali Ecommerce
├── Jubelio manual → shopsales → shopstock
├── Website        → websales  → webstock
└── Buffer         → pengaman terhadap dua ledger yang belum saling mengetahui

Buffer operasional tersebut belum tentu sama dengan jubelio.allocationPercent. Allocation adalah pengali jumlah yang dipublikasikan ke Jubelio; buffer adalah praktik operasi untuk melindungi stok fisik.

Trace Jubelio end-to-end

  1. Webhook. Endpoint POST /api/web/jubelio/webhook/salesorder berada di web API. Signature memakai SHA256 dari raw body ditambah secret. Bila secret tidak dikonfigurasi, handler yang ditinjau masih menerima webhook.
  2. Identity. Order dicari dengan pasangan site dan jub-{salesorderId}. Unique index dicoba dibuat, tetapi kegagalannya tidak menghentikan pemrosesan.
  3. SKU mapping. item_code dicocokkan ke barcode StockWizz. SKU yang tidak cocok menjadi placeholder dan pack diblokir sampai rematch.
  4. Persistence. Jubelio dibuat sebagai websales status new. Metadata channel dan warehouse ditambahkan pada tahap berikutnya; crash di antaranya dapat meninggalkan order tanpa routing lengkap.
  5. Routing. Kode memuat semua DC, mengurutkan berdasarkan lokasi dan stok, lalu memilih salah satu. fulfillmentWarehouseId channel hanya fallback, sehingga belum menjadi guard Bali-only.
  6. Claim. Claim memilih warehouse dan memeriksa stok, tetapi jalur yang ditinjau belum membuat reservasi bersama.
  7. Pack. Warehouse stock dikurangi, history ditulis, dan marker deduction disimpan. Operasi tersebut terpisah sehingga crash atau request bersamaan tetap perlu guard idempotent.
  8. Ship. Fallback deduction dipakai bila marker belum ada. Ship belum memiliki guard unmapped dan state-transition seketat pack.
  9. AWB & outbound sync. Setelah pack, StockWizz mengambil shipment/AWB dan mencoba stock sync. Target saat ini adalah on-hand × allocationPercent; belum memperhitungkan reservasi Web Sales.
06 · Lifecycle

Semua transaksi dan semua perubahan status

StockWizz perlu menyimpan status vendor apa adanya untuk audit, lalu memetakannya ke status operasional yang konsisten. Pengurangan stok harus mengikuti event yang benar-benar stock-effective di Jubelio, bukan dipilih dari nama status saja.

Raw source status

Simpan jubelioStatus, jubelioChannelStatus, timestamp event, payload reference, dan event/idempotency key.

Normalized StockWizz status

Gunakan lifecycle yang disepakati, misalnya new, processing, packed, shipped, cancelled, dan completed.

Jubelio status / eventUsulan SW statusEfek stok
Created, Pending, Paid, Confirmednew / processingBuat atau pertahankan reservasi; belum stock out
Ready to ship / PackedpackedTidak stock out bila Jubelio juga belum mengurangi on-hand
Shipped atau event vendor yang terbukti stock-effectiveshippedKurangi warehouse tepat satu kali
Cancelled sebelum stock outcancelledLepaskan reservasi
Cancelled setelah stock outcancelled_reviewJangan tambah stok sebelum return diterima fisik
CompletedcompletedTidak ada stock out tambahan
Harus divalidasi lewat sandboxStatus aktual yang mengurangi inventory Jubelio belum terbukti dari payload runtime atau kontrak vendor. Hipotesis “shipped” masuk akal, tetapi tidak boleh dijadikan aturan production sebelum membandingkan webhook event dengan perubahan on-hand per Jubelio location.

Aturan konsistensi wajib

  • Satu order line hanya mempunyai satu movement sale-out dengan key stabil, misalnya jubelio:{salesorderId}:{itemId}:sale-out.
  • Webhook duplikat tidak boleh membuat sale atau movement kedua.
  • Webhook terlambat tidak boleh menurunkan lifecycle atau menghapus flag review.
  • Status history bersifat append-only dan mencakup event inbound maupun tindakan manual.
  • Reconciliation cron memperbaiki missing order dan missing status pada existing order.

Current behavior History yang ada terutama ditambah oleh pack, ship, dan cancel manual. Update webhook existing order melakukan $set tanpa histori inbound lengkap. Reconcile cron membuat order yang hilang, tetapi melewati existing order sehingga belum memulihkan perubahan status yang hilang.

07 · Inventory

Satu sumber stok untuk Jubelio dan Web Sales

Warehouse Bali menjadi physical ledger. Semua kanal membuat reservasi pada ledger yang sama; pack atau stock-effective event mengubah reservasi menjadi movement, cancel melepas reservasi, dan return menambah stok hanya setelah barang diterima.

available Bali = warehousestock on-hand
                 − reservasi Jubelio aktif
                 − reservasi Web Sales aktif
                 − safety stock operasional

Target akhir pilot:
allocationPercent = 100%
safety / buffer   = 0

Mengapa Web Sales tidak boleh selalu mengirim adjustment -qty

Setiap event Web Sales memang harus memicu sinkronisasi ke Jubelio, tetapi aksinya adalah recalculate target lalu reconcile. Delta buta pada setiap tahap akan mengurangi stok dua kali.

Event Web SalesStockWizzJubelio reconciliation
Paid / confirmedBuat reservation BaliTarget turun sesuai active Web reservation
PackedPertahankan reservationBiasanya delta nol
Shipped / stock-effectiveOn-hand turun dan reservation dikonsumsiTarget biasanya tetap; tidak ada pengurangan kedua
Cancel sebelum shippedLepaskan reservationTarget naik
Return diterimaOn-hand naikTarget naik
Contoh satu unitAwal: on-hand 100, reservation 0, target Jubelio 100. Saat Web Sales paid: reservation 1, target 99. Saat shipped: on-hand 99 dan reservation 0, target tetap 99. Tidak ada adjustment kedua.

Untuk Jubelio-origin order, reservation milik marketplace jangan dikurangi lagi bila Jubelio sudah memperhitungkannya. Pada stock-effective status, StockWizz mengurangi warehouse satu kali lalu membandingkan target dengan observed on-hand Jubelio. Adjustment hanya sebesar selisih.

Refill

Refill tetap berasal dari StockWizz menuju Jubelio seperti implementasi yang sudah tersedia. Setiap refill harus masuk warehouse ledger lebih dahulu, dikirim ke Jubelio location yang dipetakan, lalu direkonsiliasi. Retry menggunakan key stabil dan menyimpan hasil terakhir agar keberhasilan yang responsnya terlambat tidak dikirim ulang sebagai delta baru.

08 · Product finding

Mengapa Sales tampil di semua DC

Confirmed bugbuildWebSalesDcQuery tidak memasukkan filter _fulfillment_warehouse_id. Endpoint memang menerima warehouse dari URL, tetapi query daftar dan CSV tetap mengambil semua websales.

Ada dua masalah: query global membuat semua status tampil di semua DC; selain itu, desain lama mengizinkan order new yang belum di-claim terlihat di semua DC. Keduanya bertentangan dengan keputusan bahwa Web Sales hanya dipenuhi Bali pada Phase 1.

Web Sales lama tanpa assignment perlu di-backfill ke Bali atau memakai fallback terkontrol berdasarkan website dan cutoff. Membiarkan semua DC mengklaim order tersebut menyembunyikan ownership dan memungkinkan pengurangan stok dari lokasi yang salah.

Shadow mode yang diperlukan

Harus dilakukan

  • Verifikasi signature.
  • Simpan raw payload, received time, action, status, channel status, ID dan created_at.
  • Cocokkan dengan shopsales.jubelioOrderId.
  • Pakai unique event key.
  • Laporkan missing, duplicate, unmatched, dan urutan status.

Dilarang pada shadow

  • Tidak memanggil create/update operational order.
  • Tidak mengubah websales atau shopsales.
  • Tidak mengubah shopstock, webstock, atau warehousestock.

11 · Delivery

Langkah implementasi paling aman

  1. Kunci scope Bali. Tetapkan satu warehouse Bali, Jubelio location, website, channel/store, dan cutoff. Routing, geo refine, rematch, claim, pack, dan ship harus menolak warehouse di luar allowlist pilot.
  2. Siapkan ID dan shadow mode sebelum 5 Oktober. Jadikan Jubelio Order ID wajib serta unik untuk manual sale Bali; simpan raw webhook tanpa operational writes; buat dashboard matching harian.
  3. Perbaiki ownership UI. Filter list dan CSV dengan warehouse. Backfill Web Sales unassigned ke Bali. Sembunyikan Sales Padang Galak bila tetap supply-only.
  4. Bangun lifecycle status yang aman. Mapping raw → normalized, append-only history, sequence/timestamp guard, stock-effective flag, serta aturan cancel/return.
  5. Tambahkan reservation dan idempotent movement. Gunakan key stabil per order/item/action dan transaksi atau recovery mechanism agar stock, history, status, dan marker tidak terpisah.
  6. Migrasikan saldo sekali. Rehearsal pada salinan data; cocokkan SKU, transfer, pending orders, dan physical count. Snapshot sebelum cutover. Setelah movement baru berjalan, jangan recopy snapshot Shop Stock.
  7. Aktifkan intake post-cutoff. Manual input berhenti untuk order baru. Legacy update tetap diterima tanpa warehouse deduction. Semua unknown pre-cutoff masuk exceptions.
  8. Satukan Web Sales. Mapping website → Bali warehouse, satu reservation ledger, dan reconciliation untuk semua event yang mengubah sellable stock.
  9. Stabilkan, lalu hapus buffer/allocation. Ubah allocation ke 100% untuk compatibility, observasi, turunkan buffer, lalu hapus field setelah seluruh pembaca berhenti memakainya.
  10. Rollout Jakarta setelah exit criteria Bali lulus. Ulangi snapshot, scope, cutover, dedup, dan reconciliation. Routing multi-DC tetap fase berikutnya.

12 · Outcome

Hasil yang diharapkan dan kriteria kelulusan

Hasil operasional

  • Operator tidak menginput order Jubelio baru dua kali.
  • Bali melihat pekerjaan yang memang milik Bali.
  • Padang Galak tidak lagi terlihat mempunyai Web Sales.
  • Order lama tetap dapat ditelusuri sampai selesai.
  • Exceptions memiliki owner dan tindakan jelas.

Hasil inventory

  • Satu order menghasilkan satu movement yang benar.
  • Opening + movement menjelaskan closing per SKU.
  • Jubelio dan StockWizz balance pada target sellable.
  • Web Sales tidak menyebabkan double adjustment.
  • Refill dan retry dapat diaudit.

Duplicate dan out-of-order webhook; missing webhook dan recovery cron; order bersamaan; crash di tengah multi-item movement; cancel sebelum dan sesudah stock-out; refund sesudah ship; return fisik; SKU unmapped; bundle, gift, dan rematch; stok kosong; Web Sales bersamaan dengan marketplace; kegagalan API Jubelio; retry dengan respons sebelumnya tidak diketahui; dan verifikasi tidak ada perubahan stok Jakarta.

15 · Blockers

Blocker sebelum pilot dinyalakan

  1. Jam cutoff dan daftar selected SKU belum disepakati. Target live direkomendasikan 19 Oktober, tetapi jam WITA, SKU, channel, dan batas order yang masuk pilot harus dikunci.
  2. Shadow mode belum tersedia. Ini wajib selesai sebelum rencana start 5 Oktober; mode light/dry-run yang ada tidak memenuhi definisi shadow.
  3. Status stock-effective Jubelio belum terbukti. Perlu payload nyata dan observasi perubahan on-hand per location di sandbox.
  4. Identitas Bali belum final end-to-end. Shop ID, warehouse ID, website, channel/store, dan Jubelio location harus menjadi satu mapping yang eksplisit. Scope Nusa Dua legacy juga perlu diputuskan.
  5. DC Sales belum terisolasi. Query daftar dan CSV global harus diperbaiki; order unassigned lama harus di-backfill ke Bali atau exception.
  6. Reservation bersama dan Web Sales reconciliation belum ada. Buffer tidak aman dihapus sebelum keduanya berfungsi.
  7. Idempotency movement dan durable retry belum cukup. Pack/ship bersamaan, partial failure, dan unknown external response harus mempunyai recovery yang teruji.
  8. Runtime production belum diaudit. Commit terpasang, webhook secret, unique indexes, active schedulers, legacy Shopee/Tokopedia webhook, dan konfigurasi environment belum dikonfirmasi.
  9. Opening balance belum disepakati. Perlu snapshot serta physical count per SKU; shopstock, webstock, dan warehousestock tidak boleh langsung dijumlahkan.
  10. Owner dan threshold operasional belum ditetapkan. Siapa menangani exception, batas mismatch, SLA retry, durasi observasi, dan kondisi rollback harus tercatat sebelum go-live.
16 · Recommendation

Saran saya

Gunakan 12 Oktober sebagai rehearsal gate dan 19 Oktober sebagai selected-SKU ownership cutoff.Order atau SKU di luar pilot tetap hidup pada ledger legacy; order selected SKU setelah cutoff dimiliki Bali warehouse. Ini menjaga lifecycle lama sekaligus membatasi blast radius.
  1. Jangan paksa start shadow pada 5 Oktober bila mode-nya belum benar. Lebih baik mundurkan shadow beberapa jam/hari daripada menjalankan webhook yang diam-diam menulis websales dan menciptakan duplikasi. Bila bukti shadow tidak cukup pada 16 Oktober, live pilot 19 Oktober ikut bergeser.
  2. Bekukan scope teknis Phase 1 pada Bali-only. Matikan proximity rerouting untuk pilot. Padang Galak tetap supply-only dan Jakarta tidak disentuh.
  3. Jadikan canonical Jubelio salesorder ID sebagai tulang punggung. ID tersebut menghubungkan manual sale, shadow event, post-cutover sale, report, dedup, dan reconciliation.
  4. Selaraskan stock-effective event berdasarkan bukti sandbox. Catat status, on-hand sebelum/sesudah, warehouse location, dan timing. Baru setelah itu pilih transisi yang memicu warehouse movement.
  5. Perbaiki DC Sales lebih awal. Ini quick win dengan dampak operasional besar: menghilangkan kebingungan, mencegah claim salah, dan membuat ownership terlihat jelas sebelum pilot.
  6. Pakai desired-state reconciliation untuk seluruh kanal. Web Sales memicu recalculation, bukan delta buta. Tambahkan reservation ledger dan outbox/retry sebelum buffer nol.
  7. Turunkan buffer bertahap setelah observasi. Allocation dapat dibuat 100% lebih dahulu untuk compatibility. Buffer baru menjadi nol setelah mismatch stabil, retry terbukti, dan satu siklus cancel/return selesai.
  8. Buat dashboard pilot harian. Tampilkan intake count, unmatched/duplicate, status lag, stock mismatch per SKU, failed sync, dan pending exceptions dengan owner.
  9. Dokumentasikan keputusan cutover satu halaman. Cantumkan timestamp, mapping IDs, order ownership rule, siapa menekan go/no-go, siapa menjalankan rollback, dan channel komunikasi operasi.
  10. Rollout Jakarta hanya dengan template Bali yang sudah lulus. Copy guard, checklist, dashboard, dan rehearsal; jangan sekaligus memperluas routing nasional.

Recommended decision

Go untuk shadow dan rehearsal. Selected-SKU live pada 19 Oktober hanya setelah matrix dan critical gate lulus.

Fondasi yang ada layak dipakai ulang. Mengaktifkan konfigurasi atau menjalankan migration script saat ini belum cukup untuk menjamin Bali-only routing, status penuh, satu inventory pool, dan penghapusan buffer yang aman.

Catatan. Dokumen ini adalah hasil review arsitektur dan perencanaan. Tidak ada kode StockWizz, database, webhook, scheduler, atau konfigurasi production yang diubah.
