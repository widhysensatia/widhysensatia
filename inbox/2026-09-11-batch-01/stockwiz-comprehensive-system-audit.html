01

Ringkasan eksekutif

StockWiz memiliki nilai bisnis dan cakupan luas, tetapi fondasinya belum aman untuk diperluas menjadi ERP penuh tanpa stabilisasi serius.

Kesimpulan audit

Risiko terbesar bukan tampilan lama—melainkan integritas transaksi, kontrol akses, dan sumber kebenaran data.

Sistem dapat terus dipakai dengan pengendalian darurat, tetapi ekspansi manufacturing, quality, finance, HR, sales, dan marketing akan memperbesar risiko bila model stok, security, transaction boundary, dan governance data tidak dibenahi terlebih dahulu.

06

Audit stok dan transaksi

Stock adalah risiko bisnis paling mendesak karena satu checkout dapat menyentuh sale, balance, history, customer dan loyalty tanpa atomic boundary.

01Request diulangTidak ada idempotency key global.
02Sale numberCounter increment dan read terpisah.
03Saldo dikurangiTanpa condition quantity cukup; upsert true.
04History ditulisParallel write tanpa transaction.
05Points/customerDapat gagal tetapi sale tetap selesai.

Invariant yang belum dijamin

  • Available stock tidak pernah negatif tanpa policy.
  • Satu source document menghasilkan movement tepat sekali.
  • Ledger total sama dengan balance projection.
  • Transfer out sama dengan in-transit/receipt + variance.
  • Lot, expiry, status dan custody dapat ditelusuri.
  • Posted transaction tidak diedit/hapus langsung.

Model kontrol yang dibutuhkan

  • Canonical inventory movement ledger.
  • Balance + reservation dalam transaction yang sama.
  • Atomic conditional update/row lock.
  • Idempotency table dan unique source key.
  • Reversal/adjustment workflow dengan reason.
  • Reconciliation job dan variance dashboard.
Prioritas operasional: sebelum fitur stok baru, hentikan upsert saat pengurangan, tambahkan precondition saldo, idempotency checkout, transaction boundary, dan alert jika balance/history tidak cocok.

08

Backend dan API

Backend berhasil menampung banyak kebutuhan bisnis, tetapi pola ekspansi membuat boundary dan reliability tidak lagi jelas.

Route surface terlalu luas

~556 deklarasi route di satu aplikasi meningkatkan peluang auth/validation tertinggal.

Controller dan domain bercampur

Request parsing, DB write, notification dan rule berjalan di helper yang sama.

Validation tidak seragam

Express-validator, manual parsing, defaults dan implicit coercion digunakan bersama.

Error semantics berbeda

Status code, response shape, logging dan retryability tidak memiliki kontrak universal.

Side effect tidak durable

Email/Slack/sync dapat terjadi sebelum/selepas write tanpa outbox dan exactly-once effect.

Connection ownership kompleks

AI dapat membuka MongoClient sendiri; lifecycle dan read-only boundary perlu dipusatkan.

Business config di source

ID shop/site/settings/voucher di-hardcode dan sulit divalidasi lintas environment.

API dan maintenance menyatu

Repair/migration endpoint berada di aplikasi yang sama dengan transaksi user.

Dependency/runtime tertinggal

Express 4.17, dependency lama dan Node 18 meningkatkan upgrade/security burden.

10

Testing, CI/CD, dan supply chain software

Delivery saat ini belum memberikan bukti otomatis yang sebanding dengan risiko transaksi ERP.

Kekurangan

  • Backend tidak memiliki formal test suite memadai.
  • Legacy Jest/Umi bermasalah saat audit awal.
  • Modern frontend masih memiliki failure/type error saat audit awal.
  • Sandbox workflow langsung deploy.
  • Tidak ada migration compatibility gate.
  • Tidak ada dependency/container/SBOM gate terlihat.
  • Backup/restore dan rollback tidak menjadi release evidence.

Target minimum pipeline

  1. Lint + TypeScript strict.
  2. Unit/domain tests.
  3. Integration tests dengan PostgreSQL/Mongo/Redis nyata.
  4. Critical business E2E.
  5. Migration static + rehearsal.
  6. SAST, secret, dependency, image scan dan SBOM.
  7. Build immutable artifact sekali.
  8. Canary + metrics + controlled rollback.

Reconciliation tersebar

Beberapa repair/reconcile helper ada, tetapi belum menjadi satu control dashboard dan exception workflow.

History besar satu operational DB

Report/aggregation berkompetisi dengan transaksi jika index/read path tidak dibatasi.

Backup tidak cukup tanpa restore drill

Multi-instance bergantung Redis adapter

Dashboard minimum: error/latency API, DB pool/slow query/lock, queue age/failure, outbox lag, integration retry, duplicate key, inventory variance, job last-success, dan backup last-verified.

Procurement

PR, RFQ, PO, goods receipt, QC release, supplier invoice dan three-way match belum satu lifecycle.

Finance

Belum ada double-entry GL, AP/AR, subledger, valuation, COGS, landed cost dan controlled close.

Commercial

Customer/order/fulfillment/payment/return masih terfragmentasi per channel.

CRM & consent

Unified party, consent history, segment, campaign, attribution dan loyalty ledger perlu disatukan.

HR & privacy

Attendance/leave ada; organization, payroll, overtime, training, performance dan privacy boundary perlu dilengkapi.

Master data governance

Owner, approval, effective date, duplicate rule dan change audit belum menjadi workflow lintas domain.

Internal control

Segregation of duties, approval limit, period lock, reversal dan audit evidence belum konsisten.

Roadmap perbaikan berdasarkan risiko

Urutan mengutamakan pencegahan insiden dan pembentukan bukti, baru kemudian transformasi modul.

0–30 hari · Contain

Tutup P0 dan pasang guardrail

Disable/protect AI dan mass job, hapus self-role/query HR, fail-close socket, stop token URL, upload limits, checkout idempotency dan conditional stock decrement.

30–90 hari · Stabilize

Transaction, test, dan visibility

Tentukan transaction boundary checkout, outbox, backend characterization/integration test, reconciliation dashboard, CI gates, backup/restore drill, PII redaction dan config cleanup.

3–6 bulan · Foundation

StockWiz Next foundation

PostgreSQL, modular monolith, identity bridge, RBAC scope, master data minimum, migration registry, observability, worker dan warehouse-transfer vertical slice.

6–15 bulan · Supply chain

Inventory, procurement, manufacturing, quality

Canonical ledger, lot/status, goods receipt, QC, BOM/formula, production issue/output, yield, scrap, rework dan traceability.

12–24 bulan · Commercial & finance

Unified order dan financial control

Party/customer, sales order, fulfillment, payment, returns, GL/AP/AR, valuation, COGS, tax dan close.

Kesimpulan akhir

StockWiz layak dipertahankan sebagai sumber pengetahuan bisnis, tetapi fondasi saat ini tidak boleh diperluas tanpa pengamanan. Tutup risiko P0, jadikan integritas stok dan authorization sebagai program pertama, lalu bangun StockWiz Next secara bertahap dengan PostgreSQL dan ownership data yang tegas.

Batasan dan tingkat keyakinan

Laporan ini komprehensif terhadap artefak yang tersedia, tetapi bukan penetration test atau audit compliance formal.

  • Temuan kode berasal dari working tree lokal pada 6 September 2026; perubahan setelah waktu audit dapat mengubah hasil.
  • Statistik data berasal dari database lokal stockwiz, bukan snapshot production.
  • Tidak dilakukan active exploitation, load test production, network/cloud/IAM review, secret validation, atau third-party configuration audit.
  • Jumlah route/write berasal dari pencarian statis dan digunakan sebagai indikator kompleksitas, bukan inventory API formal.
  • Audit tidak mengubah source aplikasi atau database bisnis.
  • Temuan harus dikonfirmasi melalui threat modeling, production data profiling, query explain, user observation, dan restore rehearsal sebelum program remediation besar.
