02

Prinsip dan non-goals

Prinsip ini menjadi pagar agar transformasi tidak berubah menjadi rewrite tanpa akhir.

Vertical slice lengkap

UI, API, aturan bisnis, database, permission, audit, jobs, monitoring, dan test selesai bersama.

Ownership tunggal

Setiap field dan domain memiliki satu writer resmi pada satu waktu.

Rekonsiliasi otomatis

Saldo, status, jumlah dokumen, dan nilai dibandingkan mesin, bukan hanya pemeriksaan manual.

Compatibility sementara

Adapter menjaga legacy tetap bekerja tanpa membocorkan model lama ke domain baru.

Rollback terencana

Cutover tidak dilakukan sebelum prosedur kembali dan recovery point diuji.

Data posted immutable

Koreksi melalui reversal/adjustment; bukan mengedit transaksi historis.

Yang termasuk tujuan

  • Inventory, manufacturing, QC, procurement, commercial, finance, lalu HR/CRM.
  • PostgreSQL sebagai canonical transactional store.
  • Frontend baru mengambil alih route per workflow.
  • Auditability dan traceability lot sejak fondasi.

Yang bukan tujuan fase awal

  • Menyalin seluruh fitur legacy sebelum ada pengguna.
  • Memigrasikan semua history menjadi ledger yang dianggap benar.
  • Microservices, Kafka, Kubernetes, atau data warehouse besar sejak hari pertama.
  • Mengubah semua proses bisnis sekaligus.

Pabrik migrasi MongoDB → PostgreSQL

Migrasi adalah pipeline yang dapat diulang, menghasilkan laporan error, dan dapat direkonsiliasi—bukan script sekali jalan.

01ProfileTipe, null, duplicate, orphan, volume, status.
02ExtractSnapshot konsisten ke staging raw.
03NormalizeID, email, date, money, UOM, currency.
04MapLegacy ID → canonical UUID.
05LoadMaster, active docs, opening balance, history.
06ReconcileCount, hash, amount, saldo, exception.

Urutan load

  1. Reference: currency, UOM, country, status.
  2. Organization, site, warehouse, location.
  3. Party, employee, supplier, customer.
  4. Item, identifier, price, supplier relation.
  5. Lot dan opening balance terverifikasi.
  6. Dokumen aktif dan dependency-nya.
  7. History ke partition/legacy read model.

Kebijakan exception

  • Record invalid masuk quarantine, tidak dibuang.
  • Mapping manual menyimpan actor dan alasan.
  • Duplicate merge memiliki survivor dan alias ID.
  • History lama tidak otomatis menjadi ledger resmi.
  • Setiap batch memiliki checksum dan migration run ID.
  • Production cutover memakai snapshot final + delta.
Keputusan saldo: tetapkan opening balance dari stocktake/rekonsiliasi pada tanggal cutover. History lama tersedia sebagai arsip read-only, tetapi tidak digunakan untuk menghitung saldo baru bila integritasnya belum terbukti.

Pilot pertama: warehouse transfer

Transfer gudang menyentuh ledger, reservation, approval, lot, in-transit, permission, barcode, audit, dan rekonsiliasi—cukup luas untuk membuktikan fondasi.

CreateDraft + lines
ApprovePolicy + limit
ReserveAtomic allocation
DispatchTransfer out
In transitCustody tracked
ReceiveLot + quantity
ReconcileVariance resolved
Tidak oversell

Reservation gagal secara atomic ketika available stock tidak cukup.

Double-submit aman

Idempotency key mengembalikan hasil pertama tanpa movement tambahan.

Double-entry quantity

Transfer out dan in-transit/receipt seimbang pada satu dokumen.

Lot traceable

Lot sumber, tujuan, expiry, status, dan actor dapat ditelusuri.

Posted immutable

Koreksi menggunakan reversal dan dokumen adjustment baru.

Permission scoped

User hanya dapat mengirim/menerima warehouse dalam scope-nya.

Scope pilot

  • Satu pasangan warehouse.
  • Kelompok item non-kritis tetapi representatif.
  • 5–15 key user terlatih.
  • Transaksi baru setelah tanggal aktivasi.
  • Jam support dan escalation owner jelas.

Acceptance pilot

  • 100% movement memiliki source document.
  • Selisih ledger vs balance = 0.
  • Tidak ada duplicate movement.
  • Critical E2E dan failure-path lulus.
  • Rollback rehearsal berhasil.
  • Domain owner menandatangani UAT.

Fase delivery dan exit criteria

Fase selesai karena bukti, bukan karena tanggal. Modul berikutnya tidak boleh mengorbankan stabilitas modul yang baru live.

Fase 0 · 1–2 bulan

Lindungi legacy

Tutup endpoint P0, proteksi overselling/double-submit, backup drill, runtime support, log dan alert.

Exit: risiko P0 terkendali
Fase 1 · 2–4 bulan

Platform foundation

Repository, CI/CD, PostgreSQL, identity bridge, RBAC, master data minimum, outbox, worker, observability, migration registry.

Exit: production-like environment lulus
Fase 2 · 4–6 bulan

Inventory shadow & pilot

Ledger dan transfer berjalan shadow, lalu pilot pada satu scope dengan reconciliation dan rollback.

Exit: pilot stabil 4–8 minggu
Fase 3 · 6–15 bulan

Procurement, manufacturing, quality

Goods receipt masuk inventory baru; lanjut lot/QC, formula/BOM, production issue/output, yield, scrap, rework.

Exit: traceability bahan → batch jadi
Fase 4 · 12–24 bulan

Commercial & finance

Unified party/order/fulfillment, payment, COGS, valuation, GL/AP/AR, tax, dan period close.

Exit: subledger cocok dengan GL
Fase 5 · 18–30 bulan

People, CRM, analytics, decommission

HR dan marketing dimigrasikan sesuai prioritas; route, job, collection, dan integrasi legacy dipensiunkan terkontrol.

Exit: legacy read-only lalu archived

11

Security, permission, dan audit

Security menjadi kemampuan platform dan diterapkan konsisten ke semua modul, bukan middleware opsional per route.

Identity & session

OIDC Authorization Code + PKCE, short-lived access token, secure httpOnly cookie/BFF bila sesuai, refresh rotation, logout dan session revocation.

RBAC + scope

Permission per action ditambah scope organization, plant, warehouse, shop, department, legal entity, dan approval limit.

Audit event

Actor, timestamp UTC, action, entity, before/after yang ter-redact, reason, source IP/device context, correlation ID, dan source document.

Data protection

Encryption in transit/at rest, secrets manager, PII classification, log redaction, retention, field-level access, dan controlled export.

Integration security

Signed webhook, timestamp/nonce, allowlist bila perlu, least-privilege credential, rotation, rate limit, replay protection, dan inbox dedup.

Pipeline security

Gitleaks, SAST, dependency/container scan, SBOM, patch cadence, exception dengan owner/expiry, dan scheduled DAST.

Deployment, observability, dan rollback

Release kecil dan dapat dikembalikan lebih penting daripada deployment canggih. Database compatibility menentukan strategi rollback.

Build onceImmutable image + SBOM + provenance.
Test environmentMigration + integration + E2E.
Canary scopeFeature flag user/warehouse/item.
ObserveError, latency, queue, balance, adoption.
Expand / rollbackDecision berdasarkan SLO dan reconciliation.

Minimum dashboard

  • API latency/error per route dan module.
  • Database pool, slow query, lock, deadlock.
  • Queue age, retry, failure, dead-letter.
  • Outbox pending dan integration lag.
  • Ledger–balance variance.
  • Legacy–Next reconciliation variance.

Rollback pattern

  • Expand/contract database migration.
  • Backward-compatible API satu versi.
  • Feature flag mematikan entry point baru.
  • Queue consumer dapat dipause.
  • Posted data tidak dihapus; kompensasi/reversal.
  • Runbook dan decision owner tersedia.

Checklist cutover dan decommission

Cutover memindahkan ownership, bukan hanya URL. Decommission dilakukan setelah masa observasi dan kewajiban audit terpenuhi.

Sebelum cutover modul

  • Source-of-truth matrix disetujui.
  • Migration rehearsal selesai dalam window.
  • Count, amount, balance, dan checksum cocok.
  • Open exception memiliki owner dan keputusan.
  • Critical E2E, load, security, restore lulus.
  • Feature flag, rollback, dan runbook diuji.
  • User, SOP, training, support roster siap.
  • Go/no-go ditandatangani bisnis dan teknologi.

Sebelum legacy dimatikan

  • Tidak ada writer atau job aktif ke domain lama.
  • Semua consumer menggunakan API/read model baru.
  • Integration dependency inventory lengkap.
  • Data retention dan legal hold disetujui.
  • Historical lookup tersedia.
  • Credential, queue, cron, endpoint dicabut.
  • Final backup dan restore instruction tersimpan.
  • Observasi stabil dan rollback window berakhir.

Transformasi berhasil bila operasi dan integritas data membaik, bukan karena persentase kode legacy yang ditulis ulang.

Inventory varianceSelisih ledger vs balance dan hasil stocktake; target ditetapkan per kategori.
Duplicate movementTarget nol untuk transaksi dengan idempotency key yang sama.
Traceability timeWaktu menelusuri bahan baku → batch → shipment/Customer.
Posting latencyWaktu transaksi diterima sampai saldo dan read model konsisten.
Critical error rateError pada receive, transfer, production issue, shipment, close.
Manual correctionJumlah adjustment dan intervensi data di luar workflow resmi.
User cycle timeWaktu menyelesaikan workflow dibanding baseline legacy.
Legacy retirementRoute, job, collection, dan integration yang sudah tidak memiliki writer.

Langkah keputusan berikutnya

Setujui warehouse transfer sebagai pilot, tunjuk accountable owners, bekukan invariant stok, dan jalankan fase 0 serta discovery fondasi. Pembangunan modul kedua hanya dimulai setelah pilot menunjukkan saldo konsisten, user dapat bekerja, incident terkendali, dan pola delivery dapat diulang.
