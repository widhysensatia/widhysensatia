01

Ringkasan eksekutif

StockWiz telah menjadi sistem operasi bisnis yang bernilai. Tantangannya sekarang adalah mengubah pertumbuhan organik menjadi platform ERP yang terkendali.

04

Audit lanjutan: risiko sistemik

Temuan lanjutan menunjukkan pola lintas modul. Risiko tidak berdiri sendiri; satu kelemahan dapat memperbesar dampak kelemahan lainnya.

Identity & security

Kritis

Security policy tersebar antara frontend capability, Auth0 middleware, query token, dan helper.

  • Self-service role escalation masih tersedia.
  • Token dapat dibaca JavaScript dan muncul di URL.
  • CSP mengizinkan inline script dan beberapa CDN.
  • Body JSON global menerima hingga 50 MB.

Concurrency & reliability

Kritis

Sistem belum mempunyai contract konsistensi ketika dua transaksi datang bersamaan atau request diulang.

  • Counter retail tidak dibaca secara atomic.
  • Pengurangan stock tidak memakai conditional update.
  • Tidak ada idempotency key.
  • Efek samping eksternal tidak memakai durable outbox.

Financial integrity

Tinggi

Report financial ada, tetapi belum ditopang model accounting dan precision policy yang layak ERP.

  • Uang dihitung sebagai JavaScript Number.
  • Tidak ada immutable journal dan double entry.
  • Cost, tax, dan exchange-rate rounding belum terpusat.
  • Tidak ada period lock atau approval posting.

Privacy & compliance

Tinggi

Data customer dan HR mengalir melalui banyak jalur tanpa classification dan retention policy terpusat.

  • PII muncul di log dan Slack alert.
  • Export belum mempunyai access tier dan audit download.
  • Hak HR tidak selalu HR-admin/self scoped.
  • Belum terlihat data retention dan deletion workflow.

Integration & jobs

Tinggi

Marketplace, email, website sync, dan maintenance bergantung pada endpoint serta proses web yang sama.

  • Shared token melindungi banyak job.
  • Retry/circuit breaker tidak seragam.
  • State pending sebagian hanya berada di memory.
  • Deployment ulang dapat kehilangan pekerjaan tertunda.

Delivery & recovery

Tinggi

Perubahan dapat masuk ke environment tanpa bukti otomatis bahwa workflow ERP tetap benar.

  • Backend tidak memiliki test suite formal.
  • CI sandbox langsung deploy.
  • Belum terlihat RPO/RTO dan restore drill terdokumentasi.
  • Migration tidak mempunyai version ledger resmi.

08

Arsitektur target yang disarankan

Mulai dengan modular monolith. Pemisahan microservice hanya dilakukan ketika batas domain, ownership, dan kebutuhan scaling sudah terbukti.

01 · Contract

API terstandar

Versi API, validation schema, response/error envelope, idempotency key, OpenAPI, dan permission per action.

02 · Domain

Modular monolith

Inventory, warehouse, procurement, manufacturing, order, finance, CRM, marketing, dan HR memiliki batas yang eksplisit.

03 · Data

Canonical model

Satu party/customer, satu order model, satu inventory ledger, referensi konsisten, audit fields, dan schema version.

04 · Consistency

Transaction & outbox

Write inti atomic. Email, webhook, sync marketplace, dan reporting diproses melalui event/outbox yang dapat di-retry.

05 · Control

RBAC + scope

Permission berdasarkan aksi serta scope plant, warehouse, shop, legal entity, department, dan approval limit.

06 · Delivery

Observability & tests

Correlation ID, structured audit log, metrics, reconciliation dashboard, contract test, integration test, dan E2E business flow.

09

Roadmap transformasi

Urutan ini menjaga operasi harian tetap berjalan sambil menurunkan risiko secara nyata.

Fase 0 · Lindungi

Emergency stabilization

Tutup endpoint kritis, pasang rate limit, samakan runtime, tetapkan satu lockfile, perbaiki test runner, dan pastikan backup/restore drill.

Fase 1 · Ukur

Data integrity baseline

Bangun rekonsiliasi otomatis, katalog data, definisi stok negatif, pembersihan orphan/duplicate, schema validation bertahap, dan migration registry.

Fase 2 · Satukan

Canonical inventory domain

Perkenalkan immutable movement ledger, saldo projection, reservation, in-transit, lot/status stock, transaction, dan idempotency.

Fase 3 · Modularisasi

Vertical slice pertama

Pilih warehouse transfer sebagai pilot: controller, validation, permission, domain service, repository, event, audit, dan integration test lengkap.

Fase 4 · Omnichannel

Unified order & customer

Satukan customer identity, sales order, fulfillment, payment, invoice, dan channel metadata tanpa memutus integrasi lama.

Fase 5 · ERP inti

Manufacturing, quality, procurement, finance

Bangun lot traceability dan QC terlebih dahulu, lalu formula/BOM, production order, MRP, procurement lengkap, serta double-entry accounting.

Fase 6 · Pengalaman

Migrasi frontend per modul

Frontend baru mengambil alih satu workflow utuh pada satu waktu. Route legacy dimatikan setelah parity, data, dan acceptance test terbukti.

11

Metode dan batasan audit

Audit dilakukan tanpa mengubah source code maupun database.

  • Inspeksi struktur backend, frontend legacy, frontend baru, konfigurasi build, route, helper, dan dokumentasi internal.
  • Pemeriksaan read-only terhadap nama koleksi, jumlah dokumen, index, tipe field, duplicate group, orphan reference, dan saldo negatif pada database lokal.
  • Pemeriksaan sintaks terhadap 196 file JavaScript backend: lulus.
  • Legacy test suite tidak mulai karena konflik konfigurasi Jest/Umi.
  • Frontend baru: 12 dari 14 test file lulus, 37 dari 39 test lulus; typecheck masih memiliki lima error pada kondisi working tree saat audit.
  • Temuan data lokal tidak otomatis menggambarkan database production. Production memerlukan snapshot statistik dan audit index terpisah.
  • Working tree sudah memiliki banyak perubahan sebelum audit; laporan ini tidak mengubah perubahan tersebut.
