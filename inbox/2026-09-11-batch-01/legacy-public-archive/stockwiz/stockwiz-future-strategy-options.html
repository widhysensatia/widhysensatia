Ringkasan keputusan

StockWiz baru perlu dibangun, tetapi tidak dengan cara mematikan legacy lalu menggantinya sekaligus.

02

Mengapa StockWiz perlu berubah

Masalah utamanya bukan usia framework, melainkan konsistensi transaksi, struktur domain, dan kemampuan membuktikan bahwa data bisnis benar.

Nilai yang harus dipertahankan

  • Aturan bisnis yang terkumpul sejak 2012.
  • Data historis dan pola operasi nyata.
  • Integrasi toko, gudang, marketplace, dan departemen.
  • Pengguna yang sudah memahami alur kerja.
  • Operasi harian yang tidak boleh berhenti.

Beban yang tidak boleh diwariskan

  • Banyak sumber kebenaran stok.
  • Write lintas collection tanpa transaction.
  • Otorisasi yang tidak konsisten.
  • Referensi data campuran dan orphan.
  • Model customer/order berbeda per channel.
  • Job kritis berjalan di dalam web process.
Prinsip keputusan: kita tidak sedang mengganti teknologi karena ingin terlihat modern. Kita mengganti fondasi agar stok, lot, produksi, QC, costing, finance, dan audit dapat dipercaya.

Bertahap

Keputusan frontend

Pertahankanfrontend/, React, Vite, TypeScript, TanStack Query/Table/Form, Radix, Vitest, dan Playwright.
StandarkanSatu form library, satu design system, satu date library, generated API client, error boundary, dan route-level permission.
TambahkanStorybook untuk komponen kritis, MSW untuk mock API, Decimal.js untuk kalkulasi display, dan PWA hanya untuk workflow scanner.

Keputusan backend & data

RuntimeNode 24 LTS. Gunakan satu package manager dan lockfile; rekomendasi pnpm workspace.
FrameworkNestJS memberi struktur modul/guard/DI; Fastify menjadi HTTP adapter. API terdokumentasi melalui OpenAPI.
Data accessDrizzle + node-postgres dengan SQL eksplisit. Migration harus direview; push dilarang di production.
ConsistencyPostgreSQL transaction, row locking, unique constraint, idempotency table, immutable ledger, dan outbox dalam commit yang sama.
Mengapa versi ini: Node 24 berada pada jalur LTS, PostgreSQL 18 masih didukung sampai 2030, dan frontend modern StockWiz sudah menggunakan React 19. Upgrade minor tetap dilakukan rutin; angka versi bukan alasan untuk menunda desain domain.

Referensi resmi: Node.js release schedule · PostgreSQL versioning policy · NestJS OpenAPI · Drizzle migrations

Database baru yang lebih rapi

Jangan menyalin setiap MongoDB collection menjadi tabel dengan nama sama. Desain skema baru harus mengikuti proses bisnis dan invariant.

Entitas inti

organizationssiteslocationspartiesitemsuomslotsinventory_movementsinventory_balancesreservationssales_ordersfulfillmentspurchase_ordersgoods_receiptsbom_versionsproduction_ordersquality_inspectionsjournal_entriesjournal_linesoutbox_events

Aturan desain wajib

  • Foreign key dan tipe ID konsisten.
  • Composite unique index sesuai identitas bisnis.
  • Check constraint untuk quantity, status, dan nilai.
  • numeric/decimal untuk uang dan costing.
  • Timestamp UTC; timezone hanya untuk presentasi.
  • Data posted bersifat immutable.
  • Setiap write penting atomic dan idempotent.
  • Actor, source document, reason, dan audit event wajib.

Satu model stok kanonik

ReceiveBarang masuk
ReserveAlokasi order
IssueBarang keluar
TransferAntar lokasi
ConsumeBahan produksi
ProduceHasil produksi
AdjustKoreksi terkontrol
Identitas saldo: organization + site + warehouse + location + item + lot + stock status. Status membedakan available, reserved, in-transit, quarantine, rejected, damaged, dan expired.
09

Roadmap migrasi

Migrasi dilakukan per kemampuan bisnis. Tiap fase harus menghasilkan sistem yang dapat digunakan dan diukur.

Fase 0 · 1–2 bulan

Stabilkan dan lindungi legacy

Tutup risiko keamanan dan transaksi yang tidak boleh menunggu platform baru.

  • Otorisasi endpoint, rate limit, upload limit.
  • Proteksi overselling, idempotency, dan nomor transaksi atomic.
  • Backup/restore drill, audit log, alert, dan baseline rekonsiliasi.
Fase 1 · 2–4 bulan

Bangun fondasi StockWiz Next

Identity, organization, RBAC, master data, audit, outbox, API convention, CI/CD, dan migration registry.

Fase 2 · 4–6 bulan

Pilot inventory ledger

Warehouse transfer menjadi vertical slice pertama: create, approve, reserve, dispatch, in-transit, receive, dan reconcile.

  • Mulai dari satu warehouse atau kelompok item terbatas.
  • Saldo lama dan baru dibandingkan otomatis.
  • Cutover hanya setelah acceptance criteria terpenuhi.
Fase 3 · 6–15 bulan

Procurement, manufacturing, dan quality

PR/RFQ/PO/receipt, lot traceability, incoming QC, formula/BOM versioning, production order, consumption, yield, scrap, rework, dan batch release.

Fase 4 · 12–24 bulan

Commercial dan finance

Unified party/customer, sales order, fulfillment, return, payment allocation, GL/AP/AR, COGS, inventory valuation, tax, dan closing.

Fase 5 · 18–30 bulan

Perluasan dan penghentian legacy

HR, CRM, marketing, analytics, serta decommission modul lama setelah data retention, audit, dan rollback plan disetujui.

11

Risiko transformasi dan kontrolnya

Evolutionary rebuild menurunkan risiko big-bang, tetapi tetap gagal bila disiplin data dan kepemilikan proses diabaikan.

Dua sumber kebenaran

TINGGI

Tetapkan ownership per field/domain, gunakan outbox/change capture, dan sediakan reconciliation dashboard. Hindari dual-write tanpa mekanisme pemulihan.

Scope ERP terus melebar

TINGGI

Gunakan vertical slice, outcome per kuartal, dan decision gate. Fitur baru tidak masuk bila tidak mendukung target fase aktif.

Aturan bisnis tersembunyi

TINGGI

Observasi user, katalog rule, characterization test, dan parallel run sebelum route lama dimatikan.

Data legacy kotor

TINGGI

Profiling, mapping table, quarantine record, deduplication, rehearsal migration, dan sign-off domain owner.

Microservices terlalu dini

SEDANG

Gunakan modular monolith dan event boundary. Pecah service hanya bila kebutuhan operasionalnya dapat dibuktikan.

User menolak proses baru

SEDANG

Libatkan key user sejak design, lakukan pilot terbatas, ukur waktu kerja, siapkan training dan support masa cutover.

12

Rencana 90 hari pertama

Sebelum membangun banyak modul, buktikan bahwa tim mampu mengendalikan risiko legacy dan membuat fondasi baru yang dapat diuji.

Hari 1–30

Putuskan dan ukur

  • Tetapkan sponsor, product owner, dan domain owner.
  • Setujui Opsi C serta non-goals.
  • Bekukan definisi stok dan ownership data.
  • Prioritaskan perbaikan keamanan P0.
  • Ambil baseline data dan performa.
Hari 31–60

Bangun fondasi

  • Bootstrap backend dan PostgreSQL.
  • Definisikan module boundary dan API convention.
  • Siapkan CI/CD, migration, test, observability.
  • Bangun identity/RBAC dan master data minimum.
  • Rancang ledger dan reconciliation.
Hari 61–90

Buktikan vertical slice

  • Implementasi transfer gudang happy path.
  • Tambahkan approval, idempotency, audit.
  • Uji lot/status dan kegagalan parsial.
  • Bandingkan saldo dengan legacy.
  • Demo ke key user dan putuskan pilot produksi.
13

Decision gates

Investasi dilanjutkan hanya ketika bukti pada fase sebelumnya cukup kuat.

Gate 1

Sponsor, product owner, domain owner, scope, budget, dan definisi sukses telah disepakati.

Sebelum mulai
Gate 2

Security P0 terkendali, backup teruji, baseline rekonsiliasi tersedia, dan arsitektur fondasi lolos review.

Sebelum pilot
Gate 3

Transfer gudang lulus integration/E2E test, saldo cocok, user acceptance selesai, dan rollback teruji.

Sebelum produksi
Gate 4

Pilot stabil, KPI membaik, incident terkendali, dan pola migrasi dapat diulang untuk domain berikutnya.

Sebelum scale
Gate 5

Data historis, retention, audit, dependency, dan recovery plan lengkap sebelum modul legacy dimatikan.

Sebelum decommission

Keputusan akhir yang disarankan

Mulai StockWiz Next sebagai modular monolith berbasis TypeScript dan PostgreSQL, pertahankan legacy sebagai sistem transisi, lalu migrasikan warehouse transfer sebagai vertical slice pertama. Jangan memulai full rewrite seluruh ERP dan jangan memecahnya menjadi microservices sejak awal.
