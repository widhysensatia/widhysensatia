Request 01

Automatic NET 30 Credit Validation

Mencegah PO customer atau Quote diproses menjadi Order ketika customer memiliki invoice NET 30 yang sudah overdue dan masih memiliki outstanding balance.

Doable

Proposed Solution

Validasi dilakukan di backend ketika Logistic Manager melakukan Convert Quote → Order. Frontend memberi credit-hold state dan menampilkan detail invoice yang menyebabkan block.

payment_term = NET 30 AND outstanding_amount > 0 AND due_date < validation_date → credit hold / block order conversion

Important

Jangan hanya memakai rule “invoice age > 30 days”. Due date + outstanding balance lebih aman karena ada partial payment, adjustment, dispute, atau special agreement.

TambahanTujuanStatus
Manager OverrideOrder tetap dapat diproses untuk exception yang sudah disetujui.To Confirm
Grace PeriodMenghindari false block ketika customer sudah transfer tetapi payment belum direkonsiliasi.To Confirm
Audit LogCatat siapa mencoba convert, siapa override, alasan, invoice penyebab hold, dan timestamp.Recommended
Manual Re-checkLogistics dapat cek ulang setelah Accounting memperbarui payment.Recommended

Acceptance Criteria

  • PO customer ditahan ketika terdapat invoice overdue dengan outstanding balance sesuai rule yang disetujui.
  • Nomor invoice penyebab credit hold ditampilkan kepada Logistic Manager.
  • Override hanya tersedia untuk role yang berwenang dan alasan wajib dicatat.
  • Percobaan convert, hasil validasi, dan override tersimpan dalam audit log.

Risks

  • Order valid ikut terblokir jika payment/outstanding belum ter-update.
  • Partial payment, credit note, dispute, refund, atau special agreement dapat menjadi false positive.
  • Hard block tanpa override dapat mengganggu fulfillment.
  • Frontend dan backend harus memakai rule yang sama.

Need Meeting

Ya. Ini bukan hanya technical rule — ini credit-control policy yang membutuhkan validasi Accounting dan pihak yang punya kewenangan menentukan exception.

Pertanyaan untuk Accounting / Requester

Apa source of truth piutang customer saat ini?
Due date disimpan langsung atau dihitung dari invoice date + payment term?
Rule hanya untuk NET 30 atau juga NET 14 / NET 60 / custom term?
Apakah outstanding kecil sekalipun langsung memblokir order?
Bagaimana treatment partial payment?
Bagaimana treatment credit note, dispute, refund, atau invoice correction?
Apakah dibutuhkan grace period? Hari kalender atau hari kerja?
Siapa role yang boleh override dan apakah alasan wajib?
Request 02

Automatic Invoice & Tax Invoice Delivery

Mengirim invoice elektronik dan faktur pajak secara otomatis ke customer agar proses Accounting tidak bergantung pada pengiriman manual.

Doable

Proposed Flow

Gunakan background job / queue agar proses invoice tidak gagal hanya karena email provider sedang bermasalah.

Invoice ready for delivery → resolve Invoice PDF → resolve Tax Invoice attachment (if available) → validate customer billing email → queue email → send via configured StockWizz email service → save delivery log → success / retry / manual resend

Recommended Controls

  • Status Pending / Sent / Failed / Retrying.
  • Timestamp, recipient, document reference, provider response, retry count.
  • Manual Resend untuk authorized Accounting user.
  • Action-required jika email kosong/invalid.
  • Idempotency agar event yang sama tidak mengirim email duplikat.

Acceptance Criteria

  • Email dipicu hanya ketika invoice sudah berstatus siap dikirim.
  • Invoice, Faktur Pajak, penerima, dan subject mengikuti rule yang disetujui Accounting.
  • Status Sent, Failed, Retrying, dan Manual Resend tercatat serta terlihat oleh user berwenang.
  • Retry tidak menghasilkan email duplikat untuk event yang sama.

Future Option — e-Faktur Integration

Integrasi provider seperti OnlinePajak/Mekari dapat dievaluasi di tahap berikutnya jika Faktur Pajak masih dibuat di sistem eksternal. Ini bukan MVP dan harus melalui assessment API, compliance, biaya, data ownership, dan workflow Accounting.

Request 03

Warehouse PO Tracking & Slack Notification

Memberi visibility kepada Logistics ketika staff Gudang memproses PO pada tracker.

Doable

Slack per PO

Real-time dan cepat terlihat, tetapi berisiko noisy/spam jika volume order tinggi dan histori sulit dianalisis.

Fulfillment Tracker

Lebih terstruktur untuk status, history, user, timestamp, bottleneck, dan pencarian order. Direkomendasikan sebagai source of truth.

Combined — Preferred

Tracker menyimpan operational state; Slack dipakai sebagai awareness layer untuk urgent, exception, anomaly, atau scheduled summary.

Contoh Slack Event

  • Urgent / Rush Order mulai diproses atau tertahan.
  • Stock shortage / SKU missing saat picking.
  • PO melewati SLA dan belum diproses.
  • Scheduled summary, misalnya pukul 12:00 dan 17:00.

Need Discovery

Short discovery dengan Warehouse/Logistics diperlukan untuk menentukan event yang benar-benar penting, target channel, dan volume normal supaya Slack tidak berubah menjadi notification spam.

Acceptance Criteria

  • Tracker menampilkan status PO, user, timestamp, dan history perubahan.
  • Logistics dapat menemukan PO yang pending, sedang diproses, siap dikirim, atau melewati SLA.
  • Slack hanya mengirim urgent event, exception, anomaly, atau scheduled summary yang disepakati.
  • Kegagalan proses atau notifikasi dapat dilihat dan ditindaklanjuti.

Pertanyaan untuk Warehouse / Logistics

Apa arti tepat “PO sudah di tracker”?
Status apa saja yang dibutuhkan?
Siapa audience dan channel Slack yang tepat?
Perlu setiap PO atau cukup urgent/exception/summary?
Berapa volume PO normal per hari?
Apa SLA yang dianggap terlambat?
Request 04

WEB ID Bali E-Commerce

Mendokumentasikan bahwa WEB ID pada StockWizz Bali E-Commerce sudah mengikuti ID transaksi dari website.

Confirmed

Current State

Order website sudah memiliki jalur websales sendiri dan tidak lagi menggunakan nomor transaksi retail/shop sales. WEB ID yang masuk ke StockWizz dipetakan dari ID transaksi website sehingga pencocokan data menjadi lebih konsisten.

Website order number ↓ Website → StockWizz ingestion / API ↓ websales field / reference ↓ Bali E-Commerce UI ↓ WEB ID displayed to user

Acceptance Criteria

  • WEB ID di StockWizz sama dengan reference ID pada order website.
  • Order website tercatat melalui jalur websales.
  • Tim dapat mencocokkan satu sample order dari website sampai tampilan StockWizz.
  • Perbedaan ID diperlakukan sebagai exception untuk investigasi.

Kesimpulan untuk Requester

Tidak diperlukan development untuk mengubah format WEB ID saat ini. IT cukup menyimpan satu contoh mapping end-to-end sebagai bukti referensi dan memantau jika ditemukan exception.
