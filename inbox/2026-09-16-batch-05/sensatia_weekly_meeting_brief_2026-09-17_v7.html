D1. Webhook “Fast Path” untuk operasional

Jubelio Eventorder create / update
Webhook Receivervalidate + save event
Queue / Workerasync processing
StockWizz Orderupsert + status mapping
Warehouseready for operation

Webhook jangan mengerjakan semuanya sekaligus

Receiver sebaiknya hanya verifikasi request, simpan event mentah/audit reference, cek duplicate, lalu cepat mengembalikan response sukses. Processing berat dilakukan worker di belakang. Dengan cara ini webhook lebih tahan traffic tinggi dan retry.

Payload operasional minimum

External order/transaction ID, marketplace/source, SKU, quantity, source warehouse/location, order status, shipping/courier reference, timestamp dan event version. Detail accounting tidak perlu memblokir order masuk ke gudang.

Penting: webhook + reconciliation, bukan webhook saja

Webhook bisa gagal, duplicate, terlambat, atau tidak mencakup semua perubahan. Tambahkan scheduled reconciliation/polling berdasarkan transaction yang berubah sejak last-sync sebagai safety net. Jadi webhook memberi kecepatan, API reconciliation memberi completeness.

D2. Idempotency — cegah double order / double deduction

Gunakan external unique key

Simpan Jubelio transaction/order ID sebagai integration key dan pastikan event yang sama hanya diproses sekali. Jika _sale_id memang terbukti unik 1:1 terhadap order Jubelio, field itu bisa menjadi candidate unique key.

Jangan langsung tambah unique index tanpa audit

Sebelum membuat unique index pada data existing, cek dulu duplicate lama, null/legacy rows dan apakah satu external sale memang selalu hanya boleh punya satu record. Jika semantics belum aman, lebih baik gunakan integration mapping table dengan key source + external_order_id.

D3. Status sync — canceled harus diperlakukan sebagai status kritis

Event dari JubelioRespons StockWizz yang disarankanCatatan
New / Eligible Order Create/upsert order; mapping SKU, qty, warehouse dan external ID. Idealnya buat reservation lebih dulu, bukan langsung physical deduction.
Normal Status Update Update external marketplace status tanpa merusak internal fulfillment state. Pisahkan external_order_status dan fulfillment_status jika memungkinkan.
Canceled sebelum pack Block fulfillment + release reservation / cancel order. Ini harus near-real-time agar gudang tidak packing order batal.
Canceled setelah packed Masuk exception flow / manual review. Jangan blind overwrite karena stock movement mungkin sudah terjadi.
Shipped → Refund / Return Gunakan return/refund/reversal flow. Bukan sekadar mengganti status menjadi canceled.
Saran penting soal stock deduction

Secara arsitektur, lebih aman membedakan reserved stock dan physical/on-hand stock. Order marketplace yang masuk dapat membuat reservation, sedangkan physical stock tetap berkurang saat pack/fulfillment. Kalau StockWizz saat ini belum punya reservation model, Phase 1 sebaiknya mempertahankan timing deduction yang sudah ada dan fokus dulu pada order/status sync yang idempotent agar tidak menambah risiko baru.

A. Apa yang menarik dari MC Easy?

Feature coverage

Dari demo/discussion, capability yang ditawarkan terlihat cukup lengkap untuk kebutuhan fleet tracking. Ini membuat MC Easy lebih dekat ke opsi managed solution daripada harus membangun platform sendiri dari nol.

API availability

API menjadi nilai penting karena data kendaraan berpotensi dipakai untuk dashboard internal, reporting, alerting, workflow, atau integrasi lain tanpa mengikat seluruh proses ke UI vendor.

Operational fit

Kalau reliability dan support terbukti baik saat pilot, workload internal bisa jauh lebih kecil dibanding Sensatia mengelola GPS engine, SIM, device protocol, server, alerting, dan maintenance sendiri.

B. Catatan penting: Live Assignment berbayar

Apa yang perlu dipastikan?

  • Berapa harga add-on live assignment?
  • Per kendaraan, per user, atau per account?
  • Apakah ada minimum quantity?
  • Apakah harus aktif untuk seluruh kendaraan?
  • Apakah fitur ini dibutuhkan sejak pilot atau bisa fase berikutnya?

Kenapa jangan langsung dibeli?

Kita perlu bedakan antara core GPS tracking requirement dan fitur dispatch/assignment tambahan. Kalau kebutuhan utama saat ini hanya tracking, history, alerts, reporting dan API, live assignment mungkin bisa diputuskan terpisah setelah user/business benar-benar membutuhkan.
